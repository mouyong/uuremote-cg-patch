# 根因三：视频预处理只在 Metal 上实现 —— 编码器零帧提交（2026-09-25）

## 一句话

补丁 5 类全部生效后，VT 编码会话**能建成**（`status=0`），但**从未有任何一帧被提交给编码器**
（`VTCompressionSessionEncodeFrame` 调用次数 = 0、编码器出码 = 0、Metal 纹理创建 = 0），
而采集侧一切正常（8137 帧全部被 UU 消费）。断点在「采集 delivered → 编码队列」之间，
即 UU 的**帧预处理（裁剪/缩放/格式转换）**，而该段实现**只绑 Metal**，本机无 Metal 设备。

## 运行期证据（GOT 重绑探针 uuspy2，免 sudo 注入 launchd 用户代理）

探针实现：重绑 `libstreamer.dylib` 的 `__la_symbol_ptr`/`__got` 槽位（`vm_protect` COW 改可写），
不注册 `__interpose`（避免 dlsym 自劫持）。观测函数 5 个：`VTCompressionSessionCreate` /
`VTCompressionSessionEncodeFrame` / `CVPixelBufferPoolCreatePixelBuffer` /
`MTLCreateSystemDefaultDevice` / `CVMetalTextureCacheCreateTextureFromImage`。

一次真实会话（Air 端经 `uuyc-cli device connect <DEVICE_ID>` 发起）的完整记录：

```
MTLCreateSystemDefaultDevice → nil(本机无 Metal) (返回空累计=1)
VTCompressionSessionCreate #1 1920x1080
  spec(2项): EnableHardwareAcceleratedVideoEncoder=False EnableLowLatencyRateControl=False
  → status=0 ✅成功
VTCompressionSessionCreate #2 1920x1080
  spec(1项): EnableHardwareAcceleratedVideoEncoder=False
  → status=0 ✅成功
缓冲池取缓冲 #1 status=0 0.7ms
缓冲池取缓冲 #2 status=0 0.1ms
—— 之后没有任何提交帧 / 出码 / Metal 纹理 ——
```

计数汇总（会话全程）：**提交帧=0、出码=0、Metal 纹理=0、缓冲池=2**；
同期 shim 侧：`出帧 #384/384 ... 回调进384/出384 待回0`（采集与投递完全正常）。

## 排除掉的三种反驳

1. **入口唯一性**：`nm -u libstreamer.dylib | grep -i encode` 只有 `_VTCompressionSessionEncodeFrame`
   （无 `...WithOutputHandler` 变体；解码侧才有 WithOutputHandler）→「零提交」结论成立。
2. **探针覆盖面**：全 App 扫描，只有 `libstreamer.dylib` 导入这 5 个符号（GUI 只导入 1 个）→ 没有漏看的镜像。
3. **探针自身正确性**：同一探针先在自编 VT 编码 demo 上打靶，完整看到
   `建会话 → 缓冲池 → 提交帧 ×4 → 出码 ×3（含字节数）`，机制有效。

## 本机能力基线（说明不是算力问题）

`/tmp/vt-bench`（UU 同款编码属性、无低延迟）：

- 1920x1080 编 400 帧 → 全部出码、用时 30.1s → **13.28 帧/秒**
- 1920x1080 编 200 帧 → 200 帧出码 / 218,747 字节 → **10.56 帧/秒**

UU 只需要 8 FPS。**算力富余，瓶颈在必须过的那层硬件抽象。**

## 静态旁证（为什么预处理过不去）

`libstreamer.dylib` 链接 `Metal.framework` / `MetalKit`，导入
`CVMetalTextureCacheCreateTextureFromImage` / `MTLRenderPipelineDescriptor` / `MTLSamplerDescriptor` /
`kCVPixelBufferMetalCompatibilityKey`；帧对象
`IOSurfaceExternalFrame(DesktopSize, CVBuffer, shared_ptr<MetalDevice>)` **直接持有 Metal 设备**；
预处理类只有 `VideoPreprocessSourceMac` 一种，`InputVideoBuffer::CropAndScale` 走 `IOSurfaceFrame::Texture()`；
**二进制内无 CPU 版缩放/转换实现**（无 vImage / Accelerate / CIContext 导入）。

`system_profiler SPDisplaysDataType` 中 AMD Radeon HD 6630M（pre-GCN、256MB）**无 `Metal:` 行**。

## 结论与出路

- 1~3 道门（Metal 门禁 / 低延迟 RC / 会话建立）**已被补丁打通**，属实质进展；
  第 4 道门是**架构性**的：预处理整段只有 Metal 实现，**不是 1 字节跳转能修的**（等于重写管线）。
- 现实出路按性价比：换工具（本机 ToDesk / macOS 屏幕共享，走 CPU，已验证可用）＞
  降级 UU 到重构前版本 ＞ 换支持 Metal 的机器（2014+ Mac mini / M 系列）。
