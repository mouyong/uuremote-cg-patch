# 根因四（最终）：编码器输入帧必须经 Metal 渲染 —— 第 4 道门

**日期**：2026-09-25
**对象**：UU远程 4.40.0 `/Applications/UURemote.app/Contents/Frameworks/libstreamer.dylib`（x86_64）
**本机**：2011 Mac mini（Macmini5,2），AMD Radeon HD 6630M（pre-GCN）—— **无 Metal、无 IOGPU、无硬件 H264 编码器**

## 一句话结论

`libstreamer` 被控端编码链的最后一步 —— 把**采集帧**转成**编码器输入帧** —— 实现为
**Metal 渲染管线（GPU）**：`IOSurfaceFrame::Texture()` → `CVMetalTextureCacheCreateTextureFromImage`
→ `CVMetalTextureGetTexture` → Metal command buffer 渲染。本机无 Metal ⇒ 纹理在门控处提前返回空
⇒ `Encode` 返回 `error: 12` ⇒ **VT 编码器从未被提交任何帧**（探针实测 提交帧=0、出码=0）
⇒ 零码流 ⇒ 对端永远"连接中"/黑屏。

**库内不存在该步骤的 CPU 回退实现** ⇒ 这不是 1 字节补丁可修的门控，而是**缺失能力**。

## 四道门全景

| 门 | 位置 | 性质 | 状态 |
|---|---|---|---|
| 1 | `ResetVTCompressionSession` 入口 `MTLCreateSystemDefaultDevice` 返回空 → `error: 12` | 门控（if） | ✅ 已补丁 `metal-gate` |
| 2 | 编码器规格 `EnableLowLatencyRateControl`（VT 强制硬编） | 配置 | ✅ 已补丁 `lowlat` |
| 3 | VT 会话建立（补丁后实测 `status=0`） | 依赖 1/2 | ✅ 已打通 |
| 4 | **编码器输入帧的预处理/转换只有 Metal 实现** | **架构缺失** | ❌ 无补丁解 |

## 证据链（逐指令）

### 1) 运行时探针实测（GOT 重绑，15+ 槽位）
```
采集：3504 帧 / 1920×1080 NV12 / 8 FPS / UU 回调 100% 消费
VTCompressionSessionCreate ×2 → status=0 ✅（补丁生效）
MTLCreateSystemDefaultDevice → nil（无 Metal）
提交帧（VTCompressionSessionEncodeFrame）= 0
编码器出码 = 0
CVMetalTextureCacheCreateTextureFromImage（Metal 纹理）= 0   ← 决定性
CVPixelBufferCreateWithIOSurface = 6（仅初始化）
```
`Metal 纹理 = 0` ⇒ `Texture()` 根本没走到创建纹理那一步。

### 2) 线程栈（sample）
```
EncoderQueue:
  VideoToolboxEncoderT::Encode            (0x1fc0c0)
    → GetPixelBuffer                     (0x1fc760)
      → CVPixelBufferPoolCreatePixelBuffer      （60% 采样时间）

screen_capture:
  DesktopScreenCapturer::OnFrameCallback
    → VideoPreprocessSource::OnFrame      (0x2392a0)
```

采集 + "拷进 IOSurfaceFrame" 都在跑，**卡在最后一步的 GPU 转换**。

### 3) vtable 解析（`IOSurfaceFrame` @ VA `0xb515b0`）
```
虚函数[2] +0x10  CopyFrom(RawVideoFrame)    0x235310   CPU
虚函数[3] +0x18  CopyTo(I420Buffer&)        0x235830   CPU（存在，Encode 不用）

```
`VideoFrameQueue::ConsumeEncodeFrame` 内：
```
callq *0x28(%rax)  → Valid()               通过
callq *0x20(%rax)  → CopyTo(VideoFrame&)   失败 ⇒ "preprocess output is invalid"
```

### 4) `IOSurfaceFrame::CopyTo(VideoFrame&)`（0x235850）关键指令
```
0x23594a  callq IOSurfaceFrame::Texture()          ← GPU 纹理入口
0x235959  callq IOSurfaceFrame::Texture()
0x235966  je    0x235d01                           ← 纹理空 ⇒ 失败返回
0x235a1b  callq CVMetalTextureGetTexture
0x235bc4  "Metal command buffer error: {}"          ← 必须真跑 Metal 渲染
0x235cdd  "io surface is nullptr"
```

### 5) `IOSurfaceFrame::Texture()`（0x235540）关键指令
```
0x2355cd  je    0x235700                    ← Metal 缺失时在此提前返回（探针实测未到达下一步）
0x2355d3  CVPixelBufferGetPlaneCount
0x2355dc  CVPixelBufferGetPixelFormatType
0x235605  CVPixelBufferGetWidthOfPlane / GetHeightOfPlane
0x23564d  CVMetalTextureCacheCreateTextureFromImage   ← 探针计数 = 0 ⇒ 从未执行
```

### 6) 库内确认无 CPU 回退
- `MetalDevice` **无 vtable**（纯数据持有者：`id<MTLDevice>` + `id<MTLCommandQueue>` + `CVMetalTextureCacheRef`）
  ⇒ 无法用"替换设备实现"的方式注入 CPU 版。
- `Encode`（0x1fc0c0，413 条指令）只有一条路径：
  `GetPixelBuffer` → `IOSurfaceExternalFrame(shared_ptr<MetalDevice>)` → `CopyTo(VideoFrame&)` —— **无 CPU 分支**。
- CPU 零件存在但未接通：`InputVideoBuffer::ToI420()`（0x233e40）、`IOSurfaceFrame::CopyTo(I420Buffer&)`（0x235830）、
  `VideoFrameQueue::ConsumeEncodeFrameToI420()`。
- `force_software_encoder` 是**空开关**：`CreateVideoEncoder` 4 个分支最终都创建 `VideoToolboxEncoderT`；
  全库无 VP8/VP9/openh264 实现。

## 为什么 1 字节补丁不可行

- 跳过 `0x2355cd je`（强制走纹理路径）⇒ `CVMetalTextureCacheCreateTextureFromImage(NULL, …)` 必然失败；
  且下游 `CVMetalTextureGetTexture` + command buffer 渲染仍需**真实 GPU 执行**才能把采集帧内容
  写进编码器输入 buffer。本机无 Metal ⇒ 无可绕。
- 伪造纹理对象 ⇒ 渲染命令无处执行，目标 buffer 内容仍为空 ⇒ 编码器收到空画面（且极可能崩溃）。
- 改 vtable 指针（GPU↔CPU 槽互换）⇒ 签名不兼容（`CopyTo(VideoFrame&)` 与 `CopyTo(I420Buffer&)` 目标类型不同），
  且 `Encode` 是**非虚直接调用**，改 vtable 影响不到它。

## 若要真正修好：需新增 CPU 转换模块（模块级，非补丁）

1. **注入点**：GOT 重绑无法覆盖内部直接调用 ⇒ 需在 `libstreamer` 内做指令级 trampoline
   （把 `0x23594a` 的 `callq Texture` 改写为跳到 CPU 实现），或 patch `CopyTo(VideoFrame&)` 的失败分支
   指向新增代码段（需可写段 + 代码注入）。
2. **CPU 实现**：`CVPixelBufferGetBaseAddressOfPlane`（源，NV12 双平面）
   → `CVPixelBufferLockBaseAddress` + memcpy（目标）；尺寸不等时 CPU 缩放（libyuv / vImage）。
3. **前提验证**：VT 软件编码器是否接受该目标 buffer 的像素格式与内存属性
   （采集格式 420v 与 VT pool 输出格式是否一致 —— 待实测）。
4. **工作量**：约 **2~3 天**（含验证），并需保持 `error 12` 等既有语义不变。
