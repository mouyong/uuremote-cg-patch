# 根因：UURemote 编码器被 Metal 门禁卡死（无画面）

- 机器：本机 108 = 2011 Mac mini（Macmini5,2 / i7? i5-2520M / HD6630M）+ OCLP macOS 15.7.9，无 Metal、无 IOGPU
- 对象：UU远程 4.40.0，`libstreamer.dylib`
- 日期：2026-09-25
- 症状：别的设备连上本机 → 一直「正在传输画面」，没有画面

## 一句话结论

`VideoToolboxEncoderT::ResetVTCompressionSession()` **第一步就创建 Metal 设备**（`MTLCreateSystemDefaultDevice` → `newCommandQueue` → `CVMetalTextureCacheCreate`），
本机拿不到 Metal 设备 → 函数**直接 `return false`** → 上层 `Init` 返回 `make_error_code(0xc)`（日志里就是 `failed to init VIDEO TOOLBOX encoder, error: 12`）→ 编码器永远建不起来 → 零帧 → 无画面。

★ 关键的坑：**已有的「编码器 force-software」补丁（把 `EnableHardwareAcceleratedVideoEncoder` 从 True 改成 False）根本没机会执行** —— 它在 Metal 门禁**之后**。只补那一处，行为完全不变。

## 证据链（从汇编定位）

1. 历史采样 `evidence/th.stack`（被控会话中）：`EncoderQueue` 线程两次都停在
   `streamer::encoder::VideoToolboxEncoderT<...>::CreateVideoEncoder` 内的 `_platform_strlen` / `vsnprintf`
   → 说明编码器在**反复重建**（每次失败重试），不是在编码。11 次采样 `EncodeFrame` 全 0 与此一致。
2. `VideoToolboxEncoderT::Create`（VA 0x1fab10）→ `Init`（0x1faf80）：
   ```
   0x1fb02d  movq %r14, %rdi
   0x1fb030  callq ResetVTCompressionSession
   0x1fb035  testb %al, %al
   0x1fb037  je    0x1fb057        ; false →
   0x1fb057  movl $0xc, %edi
   0x1fb05c  callq streamer::make_error_code(ErrorCode)   ; ← 日志里的 error: 12
   ```
   **error: 12 = ResetVTCompressionSession 返回 false**，不是 VT 内部的错误码。
3. `ResetVTCompressionSession`（0x1fb120）开头：
   ```
   0x1fb156  leaq -0x110(%rbp), %rdi
   0x1fb15d  callq 0x1fd000                  ; 造「MetalDevice」
   0x1fb17a  movups %xmm0, 0x90(%rbx)        ; 存 shared_ptr<MetalDevice> 到 this+0x90
   ...
   0x1fb1cb  cmpq $0x0, 0x90(%rbx)
   0x1fb1d3  je   0x1fb362                   ; 空 → 失败块
   ...
   0x1fb354  cmpq $0x0, 0x90(%rbx)
   0x1fb35c  jne  0x1fb1d9                   ; 非空 → 继续；空的落空到失败块
   0x1fb362  ... 打日志 "Failed to create metal device." ... 返回 false
   ```
4. `0x1fd000` 的反汇编：
   `_MTLCreateSystemDefaultDevice` → （nil 上发消息得 nil）→ `newCommandQueue` → `CVMetalTextureCacheCreate(..., device=nil, ...)` 返回非 0 → 返回**空 shared_ptr**。
   本机无 Metal ⇒ 必然为空 ⇒ 必然走失败块。（字符串 "Failed to create metal device." 就在这个函数里）
5. 为什么设备可以为空而编码照跑：
   - 该 `shared_ptr<MetalDevice>` 在编码器内只被**空安全**地拷贝/判空/释放：
     `Encode` 里只把它作为第 4 个参数传给 `IOSurfaceExternalFrame(...)` 构造；析构路径有 `testq/je` 保护。
   - 真正喂给 VT 的是 `VTCompressionSessionEncodeFrame(session, imageBuffer=CVBuffer, ...)`（VA 0x1fc460），走的是 **CVPixelBuffer/IOSurface 的 CPU 路径**，不需要 Metal。
   - 像素格式：`sourceImageBufferAttributes = {kCVPixelBufferIOSurfacePropertiesKey:{}, kCVPixelBufferPixelFormatTypeKey:'420v'}`（0x34323076 = NV12），
     采集侧由 CGDisplayStream + shim 负责产出 NV12（shim 已做 BGRA→NV12 转换）——与编码器要求一致。

## 已实施的修复（第 4 类补丁 metal-gate）

文件：`/Applications/UURemote.app/Contents/Frameworks/libstreamer.dylib`（x86_64 slice，VA=文件偏移−0x4000）

| 位置（文件偏移 / VA） | 改前 | 改后 | 含义 |
|---|---|---|---|
| 0x1ff1d3 / 0x1fb1d3 | `0f 84 89 01 00 00` (je 失败块) | `90 90 90 90 90 90` (6×NOP) | 设备为空也继续 |
| 0x1ff35c / 0x1fb35c | `0f 85 77 fe ff ff` (jne 继续) | `e9 78 fe ff ff 90` (无条件 jmp 继续) | 同上（两条路径都堵死） |

定位方式（版本自适应，不硬编码偏移）：扫 `48 83 bb 90 00 00 00 00 0f 84|0f 85`，再用**互指不变量**唯一配对 ——
A(je) 的目标 == B(jne) 的落空地址，且 B(jne) 的目标 == A(je) 的落空地址（本机二进制里各只有 1 处且互相吻合）。

## 验证

- `patch_tool.py` round-trip：官方原版 → 打 4 类补丁（20 字节变化）→ `unpatch` → **与官方原版逐字节完全一致**（`cmp` 通过）→ 可无损回退。
- 装机库（3 类补丁）与新补丁库的代码区差异 = **12 字节**（正是 Metal 门禁两处）+ 4 字节签名段大小字段（`__LINKEDIT.filesize` / `LC_CODE_SIGNATURE.datasize`，重签名会自动重算）。
- `patch_tool.py check`：`patched / audio patched / encoder patched / metalgate patched`。

## 残余风险 / 兜底

- 唯一不确定点：设备为空时，若有别的路径（渲染器侧 `IOSurfaceExternalFrame::Texture()` 一类）真的去用 Metal 纹理缓存，理论上可能空指针。
  编码路径已逐条核对过是 CVBuffer 直通 + 空安全拷贝；若实测崩溃，回退一步即可（`restore` / `tools/restore-app-bundle.sh`），并把崩溃报告留档。
- 装完必须**重启被控进程**（UURemoteServer），否则跑的还是旧代码。
- UU 自动更新会覆盖补丁 → 重跑 `install` 会自动重新定位（含新补丁点）。
