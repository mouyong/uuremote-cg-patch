**日期**：2026-09-25
**机器**：2011 Mac mini（Macmini5,2），AMD Radeon HD 6630M（Device ID 0x6741，Turks / TeraScale 2 = pre-GCN）→ **无 Metal**

## 一、问题与最终结论

**症状**：本机跑 UU远程，别的设备连上去永远黑屏、卡在"正在连接"。

**根因**：`libstreamer` 被控端编码链的最后一步 —— 把采集帧转成编码器输入帧 —— **只用 Metal 渲染管线实现**。
本机无 Metal ⇒ 该步必然失败 ⇒ 编码器从未收到帧 ⇒ 零码流 ⇒ 对端永远黑屏。

**修法**：运行时把该函数的 **vtable 槽**换成 CPU 实现（两平面 memcpy）。
**关键前提**：源帧与编码器输入帧都是 `420v`(NV12) 同尺寸 buffer ⇒ 无需缩放/格式转换，纯拷贝即可。

## 二、五道门（前四道在二进制/运行时，第五道是误判）

| 门 | 位置 | 性质 | 解法 |
|---|---|---|---|
| 1 | `ResetVTCompressionSession` 入口：`MTLCreateSystemDefaultDevice` 返回 nil → `error: 12` | 分支门控 | 磁盘补丁 `metalgate`（2 处跳转） |
| 2 | 编码器规格设 `EnableLowLatencyRateControl`（VT 要求硬编，本机无） | 配置项 | 磁盘补丁 `lowlat`（字面量池位移 1 字节） |
| 3 | VT 会话建立（补 1/2 后实测 `status=0`） | 依赖 1/2 | 自动打通 |
| 4 | **编码器输入帧的转换只有 Metal 实现** | **能力缺失** | **本次：运行时 vtable 槽替换为 CPU 实现** |
| （5） | 曾疑"码流没发出去" | **误判** | 实测发送正常，是观测时采集会话已结束 |

## 三、第 4 道门的取证与实现

### 3.1 定位（反汇编）

```
Encode (0x1fc0c0):
  [1fc151] callq GetPixelBuffer()            ← 取编码器输入 buffer（符号 stub 可重绑）
  [1fc1af] callq IOSurfaceExternalFrame(缓冲, Metal设备)
  [1fc201] callq InputVideoBuffer::CopyTo(VideoFrame&)
  [1fc240] 检查返回值 → 失败即 error 12
  [1fc460] callq VTCompressionSessionEncodeFrame   ← 从未到达（提交=0）

VideoFrameQueue::ConsumeEncodeFrame:
  [237d13] callq *0x28(%rax)   → Valid()
  [237d3e] callq *0x20(%rax)   → CopyTo(VideoFrame&)   ★ 虚调用，失败即丢帧
```

`IOSurfaceFrame` vtable（VA `0xb515b0`）：虚函数从 `[2]` 起，故 `*0x20` = 虚函数[6]、`*0x28` = 虚函数[7]…（`+0x30` 槽 = `CopyTo(VideoFrame&)`）

`CopyTo(VideoFrame&)`（0x235850）内部：
```
[23586d] callq *0x28(%rax)   Valid() 自检
[23594a] callq Texture()               ← 转 GPU 纹理
[235966] je 0x235d01                   ← 纹理空 ⇒ 失败返回
[235a1b] callq CVMetalTextureGetTexture
[235bc4] "Metal command buffer error: {}"   ← 必须真跑 Metal
```

`Texture()`（0x235540）内部：
```
[2355c5] cmpq $0x0, 0x88(%r14)   ← 成员 0x88 = MetalDevice
[2355cd] je 0x235700             ← 为空 ⇒ 提前返回空纹理（本机走这里）
[23564d] callq CVMetalTextureCacheCreateTextureFromImage  ← 探针实测 0 次 = 从未执行
```

### 3.2 关键实验（先验证可行性，再动手）

`/tmp/cpu-path.c` / `/tmp/zerocopy.c` 实测（40 帧）：

| 项 | 结果 |
|---|---|
| 源（采集帧 IOSurface）与编码器输入 buffer | **格式/尺寸/行长完全一致**：420v NV12 1920×1080 双平面 |
| CPU 可达性 | 直接取地址为空；`LockBaseAddress` 后可写 |
| CPU memcpy 后提交编码 | **出码 40/40 帧，0 错误** |
| CPU 拷贝开销 | 0.99 ms/帧（占编码总耗时 1.8%） |
| 编码吞吐 | **18.23 FPS**（UU 需 8 FPS，2 倍余量） |
| 尺寸不一致（1080p→720p）时直通 | 编码器也接受（内部处理） |

结论：**零拷贝直通与 CPU memcpy 都可行**；选 memcpy（改动点更少、编码器仍吃自己的 pool buffer，兼容性最好）。

### 3.3 实现（`cpupath/libuucpupath.c`）

```
运行时把 IOSurfaceFrame::CopyTo(VideoFrame&) 的 vtable 槽（2 处：IOSurfaceFrame、
IOSurfaceExternalFrame，均在 +0x30）指向 CPU 实现：
    源 buffer  = 库自带访问器 IOSurfaceFrame::CVPixelBuffer()(self)
    目标 buffer= 同访问器(dst)
    两平面逐行 memcpy（行长取小者）→ 返回 error_code{0,NULL} → 跳过 Metal
```

**版本无关设计（对 UU 更新免疫）**：
- 函数用 `dlsym` 按**导出符号**定位（`nm -gU` 确认 `__ZN8streamer14IOSurfaceFrame6CopyToERNS_10VideoFrameE` 是全局 `T`）→ 不硬编码代码地址
- 成员用**库自带访问器**（`IOSurface()` / `CVPixelBuffer()`）读取 → 不硬编码成员偏移
- 访问器按 C++ sret ABI 调用：`fn(&retbuf, self)`，返回**已 retain** 的引用，用完 CFRelease
- 任何前提不满足（buffer 不可得 / 尺寸格式不符 / 锁失败）→ **回退原实现**，不改变既有语义
- 不改磁盘文件、不改 `__TEXT`；只改运行时 `__DATA_CONST` 里的 vtable 指针（`vm_protect` COW 可写）

## 五、复现/调试要点

- 注入：⚠️ **此法已弃用**（全局变量会让系统进程加载未签名库被 SIGKILL，实测一天 141 份崩溃报告；**2026-09-28 起改走二进制级 `LC_LOAD_DYLIB`**（中间试过「UU plist 的 EnvironmentVariables」也失效了））→ 原记录：`launchctl setenv DYLD_INSERT_LIBRARIES <绝对路径>` → 重启 UU 栈
- 重启 UU 栈的正确顺序：kill 组件 → `launchctl kickstart -k gui/$(id -u)/com.netease.uuremote.agent` → `open -a UURemote`
  - **只 kill 不 kickstart** ⇒ 负责云端注册的 server 不被拉起 ⇒ 对端**一直**显示离线（本机一切正常，易误判）
  - kickstart 后若出现新旧两个 server 并存，杀掉旧的（重复注册会掉线）
- 反汇编目标：`lipo -thin x86_64` 后的薄片；`otool -tV -p '<逐字取自 nm 的符号>'`
- vtable 解析：`__ZTV<类>` VA → 按 8 字节读指针；虚函数从 `[2]` 起
- sret ABI：`fn(&retbuf, self)`；CFRetain 语义：返回值为已 retain，调用方 Release
- 关键常量：VA = fileoff − 0x4000；`IOSurfaceFrame` vtable `0xb515b0`；`CopyTo(VideoFrame&)` `0x235850`
- 诊断日志：`/tmp/uucpu.log`（修复）、`/tmp/uudump.log` + `/tmp/uu.h264`（码流）、`/tmp/uusend.log`（发送）、`/tmp/uushim.log`（采集）

## 六、必须告诉使用者的代价

- **代价**：软编吃 CPU。本机 8 FPS 软编约占一个核的 44%（UURemoteServer ~90% 单核 + VTEncoderXPCService ~112%）
  ⇒ 被控期间本机 CPU 负载明显升高，属正常。
- **含 1 个未消除的依赖**：磁盘补丁（第 1、2 道门）需 sudo 安装，UU 更新后要重跑。
- **不动协议/网络行为**：只把本机这一侧的帧转换从 GPU 换成 CPU，不改协议、不改上传对象、不改对端逻辑。
- **适用面**：凡"无 Metal 但能软编 H.264"的 Mac 都适用（本机实测软编 18 FPS > 需求 8 FPS）。
- 这是**本机兼容性修复**，不是厂商 bug；若官方后续提供软件渲染开关，应改用官方开关。
