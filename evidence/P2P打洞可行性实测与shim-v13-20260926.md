# P2P 打洞可行性实测 + shim v13

日期：2026-09-26（凌晨）
机器：108 = 2011 Mac mini（`<LAN_IP_108>` / VPN `<VPN_IP_108>`）；101 = MacBook Air M2（`<LAN_IP_101>` / VPN `<VPN_IP_101>`）

## 一、问题

用户问：108 与 101 之间「P2P 打洞」是否可行；并指出「既然要打洞，就不该走 VPN 网络」。

**方法合规性**：打洞实验的 UDP 全部用 `IP_BOUND_IF` 绑定物理网卡（108=en1，101=en0），
VPN 仅用于 SSH 交换双方映射地址（信令，几十字节），与真实打洞流程一致 —— 未走 VPN 承载媒体。

## 二、实验与结果

### 1. 两机不在同一二层网络（先排除「局域网直连」）
| 测试 | 结果 |
|---|---|
| 108 → `<LAN_IP_101>` | 100% 丢包 |
| 101 → `<LAN_IP_108>` | 100% 丢包 |
| 101 的 ARP 表 | 无 `<LAN_IP>` 条目 |
| Clash TUN 关闭后再测 | 同上（此前 0.37ms「ping 通」是 ClashX TUN 假象） |

### 2. NAT 类型（同一 socket 打多个 STUN 服务器）
| | 108 | 101 |
|---|---|---|
| 公网映射 | **4 个不同 IP+端口**：`<PUBLIC_IP_1>` / `<PUBLIC_IP_2>` / `<PUBLIC_IP_3>` / `<PUBLIC_IP_4>` | **1 个**：`<PUBLIC_IP_5>`（全部一致） |
| 判定 | 多出口 + 端口相关（最差） | EIM 锥形映射 |
| 端口可预测性 | 递增 +1 | 递增 +1~2 |

### 3. 双向同时打洞
- 108 发出 **966** 包 → 收到 **0**
- 101 发出 **2280** 包 → 收到 **0**
- 在 101 网卡 `sudo tcpdump -n -i en0 'udp and not net <LAN_IP>'`：**一个来自 108 的包都没到**

### 4. 结论
**公网 P2P 打洞不可行**。原因：108 是多出口对称 NAT，其源 IP 对每个目的地都不同，
对端永远学不到「该回哪个地址」→ 死锁；再叠加 EIM≠EIF（101 只有它主动联系过的地址能打进）。
UU 选 `UDP relay` 是它在算出的候选里唯一的出路，不是配置没开。

### 5. 替选方案实测
| 路径 | UDP 往返 RTT |
|---|---|
| UU 中继 | 132 ms |
| **VPN 直连（同 <VPN_SUBNET>）** | 最小 52 / **中位 57** / 最大 125 ms |

双方在同一虚拟子网 ⇒ 互为 host candidate，无需 NAT 穿透，**比「真 P2P」更划算**。

**收益提醒**：用户浮层显示总延迟 724ms，其中网络仅 ~66ms；打洞最多省 ~14%，
瓶颈是整机过载（load 曾达 63.68，2 核 4 线程）。

## 三、v12 验证 + v13 新发现

### v12 已生效（用户自装）
- `流数超上限 8` 最后出现于 `00:03`，v12 于 `00:05:17` 加载 → **之后 0 次**（槽位泄漏已修）
- 00:05–00:33 连续 8 次 `create idx=0..7` 均正常

### v13 修的问题（本轮新发现）
`00:33:18` 会话 `CVPixelBufferCreate` + `IOSurfaceCreate` 双双失败（`-6662`，系统可用页仅 19MB，
Docker 虚拟机占 1.64GB）→ 该会话无帧；**且采集线程仍被启动**，导致：
- `sample` 栈顶停在亮度自检 `movzbl 0x1(%rcx,%rdi,4)`（`%rcx = s->buf`，已释放）
- 循环末尾 `if (wait > 0) usleep()` 在耗时超预算时**完全不睡** → 满速空转
- **实测：无会话时 `UURemoteServer` 长期烧 55~62% CPU**；重启进程后回落 **0.8%**

v13 三处修改：就绪守卫（缓冲未就绪则 50ms 跳过）、限速保底 5ms、`my_start` 分配重试 8×300ms
（仍失败则不启动采集线程并返回 -1）。

产物：`~/.hermes/uuremote-cg-patch/shim/libuushim.dylib`（= `libuushim_v13.dylib`，33000 字节），
安装：`sudo bash ~/.hermes/uuremote-cg-patch/uu-shim-install.sh`。

## 五、⚠️ 更正：`<VPN_SERVER_IP>` 是用户自己的 VPN 服务器，不是 UU 中继

上一版把 `<VPN_SERVER_IP>:1194` 写成「腾讯云 UU 中继节点」——**错误**。
`lsof -nP -iUDP | grep <VPN_SERVER_IP>` 显示持有者是 **OpenVPN 客户端（pid 799）**；
`~/Library/Application Support/OpenVPN Connect/profiles/bundled.ovpn` 里写着
`remote <VPN_SERVER_IP> 1194 udp`（**1194 = OpenVPN 标准端口**）。
教训：报「走哪个节点」必须先用 `lsof -a -p <进程>` 确认持有者，不能凭 netstat 里的公网 IP 猜。

### 媒体流实际路径（接口字节计数器实测）
| 接口 | 上行速率 | 含义 |
|---|---|---|
| `utun4`（VPN 隧道） | **0.3 KB/s** | 几乎空载 |
| `en1`（物理网卡） | **39.7 KB/s** | **视频流走这里** |

⇒ 当前手机会话的媒体流**没有走 VPN**，是经物理网卡直出到 UU 中继。

### VPN 路径 RTT 实测（用于回答「走自己 VPN 会不会更快」）
| 路径 | RTT |
|---|---|
| 108 → VPN 服务器 `<VPN_SERVER_IP>` | **10.4 ms** |
| Air(101) → VPN 服务器 | **44.1 ms** |
| 108 → Air（经 VPN 隧道 `<VPN_IP_101>`） | **60.3 ms** |
| UU 中继（对照） | **132 ms** |

⇒ 若控制端也加入 VPN（双方同 `<VPN_SUBNET>`，互为 host candidate、无需 NAT 穿透），
网络 RTT 可由 132ms 降到 ~60ms（**2.2 倍**）。但总帧延时 724ms 里网络仅占 ~66ms，
**换算下来只改善约 10%**：手感会明显变跟手（键鼠 RTT 减半），**但帧率/卡顿治不了**。

## 六、性能病根：内存耗尽 + 疯狂换页（不是 CPU 算力）

| 指标 | 数值 |
|---|---|
| 交换区 | **6144 MB 中用了 5151 MB（~84%）** |
| 换入/换出累计 | 4560 万 / 5671 万页 |
| 可用内存 | ~24 MB |
| load average | **47.67 / 35.75 / 20.92**（2 核 4 线程） |

病灶：**Docker Desktop 的 VM 常驻 1681 MB**（`--memoryMiB 4096`、`--cpus 2`），
而内部只跑 **1 个** mysql 容器（`syntestdb`，249 MB）。
→ 8GB 机器内存被吃光 ⇒ swap 满 ⇒ 换页把 load 推到 47~69 ⇒ 采集每帧等内存 ⇒ 帧率崩到 4.4~6.2 FPS。
**结论：先停 Docker，再调任何帧率参数**（否则是在错参数上做优化）。

## 八、v13 → v14：槽位累积泄漏（「又连不上」的真因）+ 看门狗

### 症状
用户报「这会又连不上了」。取证：`CVPixelBufferCreate -6662` + `BGRA 回退也失败`
+ `start：无可用缓冲` → 该会话无帧 → 黑屏。但**机器本身分配正常**
（独立探针 3/3 成功，可用内存 427MB）⇒ 是 **UURemoteServer 进程内**资源耗尽。

### 根因（两条，都在 shim 里）
**① start 失败的会话永久占用槽位。**
UU 对 `CGDisplayStreamStart` 返回失败的会话**不再调用 stop**，于是该槽位
`started=0 且 released=0` —— 连 v12 的回收条件（`!started && released`）都不满足，
**永远不可回收**。实测 `create` 61 次只配到 `stop` 46 次 ⇒ **15 个槽位永久泄漏**，
进程 RSS 涨到 **1720MB**（正常约 50~270MB），且 **17336 个 IOSurface 区域**
（泄漏铁证）→ create 只能返回「无采集线程的假句柄」→ 黑屏。

**② 回收逻辑只在槽位全满时才跑。** `if (idx < 0) { 回收 }` —— MAXS=32，槽位用到 19
就还有空位 ⇒ **回收从不触发**（日志 `槽位回收` 恒 0）。

### 修法（v14）
- 新增 `slot_detach(s)`：把会话从槽位表摘除（让出槽位号），但**刻意不 free(s)、不
  CFRelease(handle)** —— UU 可能仍持有该句柄并之后调 stop/getRunLoopSource，
  释放会 use-after-free；摘除后 `lookup()` 返回 NULL，走「未知句柄」安全分支。
  代价仅每死一个会话泄漏 ~200 字节结构体（vs 原来泄漏 3 个 IOSurface ≈ 25MB）。
- `my_start` 缓冲仍不可用时：打日志 + `slot_detach(s)` + return -1。
- `shim_create` 里**主动**回收「create 后超 60 秒仍未 start」的陈旧死槽位（第二道保险）。
- 新增 `created_ms` / `dead` 字段；版本串 → v14。

### 看门狗（`uu-watchdog.sh` + `uu-watchdog-loop.sh`）
- 判据：① RSS > 3000MB（硬顶，兜失控泄漏）② 已 >60s 无出帧 **且** 出现 `流数超上限`/
  `分配失败≥3`/多实例 → 恢复（`pkill -x UURemoteServer` + `launchctl kickstart agent`）。
- **铁律：还在出帧就不动它**（重启会踢掉正在用的用户）；唯一例外是 RSS 硬顶。
- 冷却 180 秒（`/tmp/.uushim-watchdog-last`），防故障持续时反复重启。
- 交付前做了 **5 项双向对照测试**（`/tmp/wd_test.py`）：好样本必须放过、坏样本必须报警、
  陈旧故障必须放过、冷却必须拦住 —— 一次跑出 **3 个真 bug**（见下）。
- 部署：`launchctl bootstrap` 被网关限制 → 用**双保险**：常驻循环脚本（当前会话）+
  `~/Library/LaunchAgents/com.uuremote-cg-patch.watchdog.plist`（登录/重启后自动加载）。

### ★ 三个只有做对照测试才能发现的 bug（都值得记住）
1. **`"${VAR}"#` 缺空格**：bash 把 `#` 并进了变量值，下一行的 `RSS` 被当成命令 →
   `RSS: command not found` + `set -u` 下 unbound variable。
2. **`pgrep -f '路径'` 会把调用它的 shell 自己算进去**（命令行里含该字样）→ 误报「多实例」。
   必须用 `pgrep -x <进程名>`（按进程名精确）。
3. **用字符串比较取「最近 N 秒」在跨午夜时彻底失效**：日志里有昨天 `23:55`，
   而 `"23:55" >= "01:24"` 字典序为真 ⇒ 把**昨天的故障**当成刚发生 → 看门狗会误触发重启。
   正确做法：HH:MM:SS → 秒数，与**墙钟当前时刻**做差（跨午夜 `+86400`）。
   基准也不能用「日志最后一行的时间」（空闲时它早于故障行）。

### ★ RSS 不能当可靠的故障信号（会误杀）
会话进行中 `UURemoteServer` 的 RSS 实测可达 **1~1.8GB**，且**在 1.1~1.8GB 间波动、
有时回落到 21MB**（IOSurface/编码器缓冲的池化保留，非单调泄漏）。
把阈值定低（如 500MB）会导致看门狗**每次都在用户正用时重启**。故硬顶取 3000MB，
主要判据改用「已停流 + 故障日志」。

### 环境注记
- **Docker 会自动回来**：用户 01:0x 退出后，**01:23:14 又自行启动**，VM 常驻 1835MB，
  swap 回到 87%。要真正释放内存需同时关闭 Docker Desktop 的开机自启
  （`Docker Desktop → Settings → General → 取消 Start Docker Desktop when you sign in`）。
- 收尾状态：设备 `online=True`、server 单实例、看门狗无动作、`流数超上限` 增量 0。
